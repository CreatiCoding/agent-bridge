# 서버 설정 파일 bridge.yaml

이 가이드를 마치면 서버 설정을 `bridge.yaml` 파일 하나에 모아 두고, 환경 변수만 쓰던 서버를 그 파일로 옮길 수 있어요. 모든 키와 기본값은 [bridge.yaml 키](/reference/config)를, 환경 변수 목록은 [환경 변수](/reference/env)를 보세요.

## bridge.yaml 이 뭔가요

`bridge.yaml` 은 서버가 시작할 때 한 번 읽는 설정 파일이에요. 환경 변수로는 담기 어려운 설정을 여기에 둬요.

- 기능 끄기: 다른 맥으로 옮기기, 웹 푸시, 음성, 미리보기, 스킬, Slack, 키 버튼
- 고를 수 있는 권한 모드
- 업로드 보관 시간, 세션 미리보기 문구를 남길지
- 조작 페이지에 넣을 그림·프레임 출처(CSP), 처리방침 파일
- 앞단 프록시의 헤더 로그인과 여러 출처
- 이벤트 웹훅, 서버 훅, 익스텐션

파일이 없으면 서버는 지금처럼 환경 변수만 써요. 파일을 꼭 만들어야 하는 건 아니에요.

몇몇 키는 같은 뜻의 환경 변수가 있어요. 그 환경 변수는 그 키의 기본값이고, 파일에 적은 값이 이겨요.

| 키 | 같은 뜻의 환경 변수 |
|---|---|
| `origins.primary` | `BRIDGE_ORIGIN` |
| `auth.allow` | `GITHUB_ALLOWED_LOGINS` |
| `auth.admins` | `BRIDGE_ADMIN_LOGINS` |
| `retention.allowPurge` | `BRIDGE_PURGE` |

값에는 `${NAME}` 으로 환경 변수를 넣을 수 있어요. 비밀값은 파일에 직접 쓰지 말고 이렇게 넣으세요.

## 파일 위치

기본 위치는 데이터 폴더의 `bridge.yaml` 이에요. 이미지에서는 `/data/bridge.yaml` 이에요.

다른 곳에 두려면 `BRIDGE_CONFIG` 에 **절대 경로**를 넣으세요. 읽기 전용으로 마운트해도 돼요.

```yaml [docker-compose.yml]
services:
  bridge:
    # …서버 올리기의 설정 그대로…
    volumes:
      - bridge-data:/data
      - ./bridge.yaml:/etc/bridge/bridge.yaml:ro
    environment:
      BRIDGE_CONFIG: /etc/bridge/bridge.yaml
```

서버는 uid 1000 사용자로 돌아요. 파일 권한을 `0644` 로 두어 그 사용자가 읽을 수 있게 하세요.

::: warning 파일을 바꾸면 다시 시작해야 해요
서버는 시작할 때 한 번만 읽어요. 파일을 고친 뒤에는 서버를 다시 시작하거나 다시 배포하세요.
:::

::: danger 파일이 틀리면 서버가 시작하지 않아요
모르는 키, 틀린 값, 비어 있는 `${NAME}` 이 있으면 서버는 시작하지 않아요. 로그에 `설정 파일 오류로 시작하지 않습니다: 3번째 줄: …` 처럼 줄 번호와 이유가 찍혀요. 다시 시작하기 전에 아래 "검사" 로 먼저 확인하세요.
:::

::: details 파일 위치의 세부 규칙
- `BRIDGE_CONFIG` 가 상대 경로면 시작하지 않아요.
- 기본 위치에 파일이 없으면 "파일 없음" 이에요. `BRIDGE_CONFIG` 로 정한 파일이 없으면 시작하지 않아요. 마운트가 빠진 채로 설정 없이 뜨지 않게 하려는 거예요.
- 그 자리가 폴더면 시작하지 않아요. 없는 파일을 `-v` 로 마운트하면 Docker 가 폴더를 만들어요.
- 0바이트이거나 주석·빈 줄뿐인 파일은 "파일 없음" 과 같아요.
- 컨테이너가 root 로 시작하면, 데이터 폴더 안의 설정 파일은 uid 1000 에게 넘기기를 한 번 시도해요. 데이터 폴더 밖의 파일은 바꾸지 않아요. 그 뒤 uid 1000 이 파일과 위 폴더들을 지나 읽을 수 있는지 보고, 못 읽으면 시작하지 않아요.
- [끊기지 않는 배포](/guide/operate/deploy)로 바꿀 때 새 설정으로 시작하지 못하면, 옛 서버가 전 설정 그대로 계속 일해요. 운영 탭에는 `새 설정으로 시작하지 못했어요` 가 보여요.
- 시작하지 못하면 데이터 폴더에 `config-error.json` 을 남겨요. 정상으로 시작한 서버는 이 파일을 지워요.
:::

## 환경 변수만 쓰던 서버를 옮기기

운영 탭이 지금 환경 변수로 파일을 만들어 줘요. 이 파일에는 값 대신 환경 변수 참조만 들어가요. 그래서 비밀값이 들어가지 않고, 넣어도 동작이 그대로예요.

1. 설정 → **운영** → **설정 파일** 에서 **설정 파일로 내보내기** 를 누르세요.
2. 시트에 나온 내용을 복사하거나 내려받으세요. 이런 모양이에요.

   ```yaml [bridge.yaml]
   # bridge.yaml: 이 서버의 환경변수에서 만든 설정 파일 (REQ-F-810)
   # 만든 때 …, 서버 …
   # 값 대신 환경변수 참조만 적었습니다. 환경변수를 고치면 지금처럼 반영됩니다.
   # 같은 뜻의 환경변수를 지우지 마세요. 이전 버전으로 되돌리면 그 버전은 환경변수만 읽습니다.
   origins:
     primary: "${BRIDGE_ORIGIN:-}"
   auth:
     allow: "${GITHUB_ALLOWED_LOGINS:-}"
     admins: "${BRIDGE_ADMIN_LOGINS:-}"
   # 이 서버가 더 받는 키: …
   ```

3. 그 내용을 [파일 위치](#파일-위치)에 두세요. 파일 마운트로 넣는 걸 권해요.
4. 시트의 **붙여 넣고 검사** 에 고친 내용을 넣고 검사하세요. 저장하지 않고 검사만 해요.
5. 서버를 다시 시작하거나 다시 배포하세요. 운영 탭의 설정 파일 줄에 `있음 · … · 이번 시작에 읽음` 이 보이면 돼요.

파일 마운트 대신 시트의 **이 서버에 저장** 을 눌러도 돼요. 기본 위치에 파일이 없을 때만 보여요. 데이터 볼륨에 바로 쓰기 때문에, 그 뒤로는 컨테이너 터미널에서만 고칠 수 있어요.

::: tip 같은 뜻의 환경 변수는 지우지 마세요
옮긴 뒤에도 `BRIDGE_ORIGIN` 같은 환경 변수는 그대로 두세요. 이전 버전으로 되돌리면 그 버전은 환경 변수만 읽어요.
:::

컨테이너 안에서 명령줄로도 할 수 있어요.

```sh [터미널]
docker exec bridge /app/bridge-server config export   # 참조만 담은 파일을 표준 출력에
docker exec bridge /app/bridge-server config check    # 지금 위치의 파일 검사
docker exec bridge /app/bridge-server config check /etc/bridge/bridge.yaml
```

::: details 내보내기·저장·검사의 세부 규칙
- **내보내기**는 위 표의 네 키 중 환경 변수가 설정된 것만 `키: "${환경변수:-}"` 로 적어요. 설정 안 된 키는 맨 아래 주석에만 적어요. 설정 파일이 이미 있으면 내보내기를 주지 않아요(409 `이미 설정 파일이 있어요. …`). 붙여 넣으면 지금 파일의 다른 설정이 사라지기 때문이에요. 그때 시트는 **보기·검사** 로 바뀌고, 지금 파일을 가려서 보여 줘요.
- **이 서버에 저장**은 `BRIDGE_CONFIG` 를 정하지 않은 서버에서만 돼요(아니면 409). 서버를 바꾸는 중이면 503, 이미 파일이 있으면 409, 주석만 있는 파일이 있으면 409, 마운트된 빈 파일이라 지울 수 없으면 409 `마운트된 파일이라 여기서 쓸 수 없어요…` 예요. 내보낸 내용을 먼저 검사해서 통과하지 못하면 422 로 쓰지 않아요.
- **붙여 넣고 검사**는 위 표의 네 환경 변수와 지금 파일이 이미 쓰는 이름만 치환해요. 다른 이름이 있으면 검사하지 않고 그 이름을 알려 줘요. 붙여 넣은 글로 이 서버의 다른 환경 변수(비밀값)를 떠보지 못하게 하려는 거예요. 그 이름을 쓰려면 파일을 둔 뒤 **지금 파일 검사** 로 확인하세요.
- **지금 파일 검사**는 디스크의 파일을 지금 환경 변수로 검사하고, 파일에 적은 익스텐션도 불러 봐요. 불러오지 못한 익스텐션은 경고로만 보여요.
- 화면·검사 결과·명령줄에 보이는 파일 내용과 오류는 가려요. 키 이름에 `secret`·`password`·`passwd`·`token`·`apikey`·`api_key`·`privatekey`·`private_key`·`credential` 이 든 값은 `***`(대소문자 구분 없음, `key` 만 든 이름은 가리지 않아요), 주소의 경로·쿼리는 `…`, 주소의 `user:password@` 는 지워요.
- 명령줄 `config check` 는 판정한 서버 사용자(uid)와, 그 사용자가 파일을 못 읽으면 실패를 알려요. 종료 코드는 0 통과, 1 실패, 2 사용법이에요. 이 명령은 파일을 만들지 않고 떠 있는 서버에 손대지 않아요.
- 파일 값이 같은 뜻 환경 변수와 다르고, 환경 변수 참조가 아니고, 환경 변수가 설정돼 있으면 운영 탭 맨 위에 `환경변수 … 를 고쳐도 반영되지 않아요` 경고가 떠요. 시작 로그에도 같은 뜻의 줄이 찍혀요.
:::

::: warning bridge.yaml 을 모르는 옛 이미지에서는 config 명령을 돌리지 마세요
1.347 판보다 옛 이미지의 서버는 `bridge-server config …` 를 서버 실행으로 받아, 떠 있는 서버에 교체를 걸어요.
:::

## 흔한 설정

### 기능 끄기

쓰지 않을 기능을 끄면 그 API 가 403 `이 서버에서 꺼진 기능이에요` 로 거절하고, 화면은 그 입구를 숨겨요.

```yaml [bridge.yaml]
features:
  voice: false        # 음성 탭·입력창 마이크
  slack: false        # Slack 플러그인
  sessionMove: false  # 다른 맥으로 옮기기, 다른 맥에 일 맡기기
  permissionModes: [default, acceptEdits, plan]   # 전부 허용은 고를 수 없게
```

`default` 는 화면의 "manual", `acceptEdits`·`plan` 은 화면에서도 같은 이름이에요. 위 예처럼 적으면 `auto` 와 전부 허용 두 가지(`autoAllow` "안전한 전부 허용", `allowAll` "전부 허용")는 화면에서 고를 수 없어요. 목록 밖 권한 모드로 시작하려는 세션은 거절하지 않고 `default` 로 낮춰요. 키 이름과 화면 이름 표, 키마다 숨기는 곳은 [bridge.yaml 키](/reference/config#features)를 보세요.

::: tip 가드레일이에요
권한 모드 목록은 화면과 서버 API 를 막아요. 맥에서 직접 바꾸는 것까지 막지는 않아요.
:::

### 보관 기간

```yaml [bridge.yaml]
retention:
  uploadsHours: 6     # 맥이 받지 못한 업로드를 6시간만 보관(기본 24)
  previews: false     # 세션 기록에 미리보기 문구를 남기지 않음
```

`previews: false` 면 시작할 때 읽은 세션 기록의 미리보기도 비워요. 다음에 저장할 때 파일에서도 빠져요.

### 앞단 프록시의 헤더 로그인과 여러 출처

회사나 팀 안에서 SSO 프록시 뒤에 서버를 둔다면, 프록시가 확인한 사람을 헤더로 받아 로그인시킬 수 있어요. GitHub OAuth App 이 없어도 돼요.

```yaml [bridge.yaml]
origins:
  primary: https://bridge.example.com
  extra:
    - https://bridge.internal.example.com
auth:
  providers:
    - type: trusted-header
      userHeader: X-Auth-Email        # 프록시가 넣는 사용자 이메일
      secretHeader: X-Bridge-Proxy    # 프록시가 넣는 공유 비밀
      secret: "${PROXY_SECRET}"       # 16자 이상, 환경 변수로 넣기
      trustFrom: [10.0.0.0/8]         # 프록시의 주소
  admins: [admin@example.com]
```

요청의 `secretHeader` 값이 `secret` 과 같고, 요청을 보낸 TCP 주소가 `trustFrom` 안일 때만 `userHeader` 를 믿어요. 그 이메일이 그 사람의 로그인 이름이에요. 허용 목록과 운영자 목록에 이메일을 그대로 적으면 돼요. 허용되지 않은 사람은 GitHub 로그인처럼 승인 대기 화면을 보고, 운영 탭의 접근 관리에 올라와요.

`origins.extra` 를 두면 한 서버를 여러 주소로 열 수 있어요. 그 밖의 주소로 온 요청은 421 `이 서버의 주소가 아니에요` 로 거절해요. 맥 연동은 `origins.primary` 에서만 해요.

::: danger 프록시는 같은 이름의 헤더를 지우고 넣어야 해요
프록시는 손님이 보낸 `userHeader`·`secretHeader` 를 지우고 자기 값을 넣어야 해요. 서버 포트는 프록시만 닿게 두세요. `trustFrom` 은 `X-Forwarded-For` 가 아니라 실제 연결 주소로 비교해요.
:::

헤더 로그인만 받으려면 `auth.headerOnly: true` 를 더하세요. 켜면 GitHub·QR 로그인과 헤드리스 연동이 닫히니, 먼저 **붙여 넣고 검사** 로 확인하세요.

::: details 헤더 로그인의 세부 규칙
- `auth.headerOnly: true` 면 GitHub·Apple·데모·QR 로그인이 모두 닫혀요.
- 헤더 없이 온 요청은 로그인 쿠키가 있어도 로그인하지 않은 것으로 봐요.
- 맥의 화면 없는 브라우저는 SSO 를 지나지 못해서 헤드리스 연동도 쓸 수 없어요.
- 그 파일을 **붙여 넣고 검사** 하면, 헤드리스 연동을 먼저 꺼야 할 기기가 `헤더 로그인만 받기 전에 이 기기들의 헤드리스 연동을 끄세요` 아래에 보여요.
- `auth.providers` 의 항목은 다섯 필드가 모두 있어야 해요. `type` 은 `trusted-header` 하나만 받아요. 항목도 하나만 둘 수 있어요.
- `userHeader`·`secretHeader` 는 영문·숫자·`-` 로 된 1~64자 헤더 이름이에요. `Cookie`·`Host` 는 안 되고, 둘이 달라야 해요.
- `trustFrom` 은 IP 주소나 CIDR 목록이에요. IP 하나는 `/32`(IPv6 는 `/128`)로 봐요.
- 비밀은 SHA-256 끼리 상수 시간으로 비교해요.
- 사용자 헤더 값은 앞뒤 공백을 지우고 소문자로 바꿔요. 이메일 주소가 아니면 401 `프록시가 보낸 사용자 헤더(<userHeader>)가 이메일 주소가 아니에요` 예요. 이메일이 바뀌면 다른 사람이에요.
- 허용된 사람이면 다른 로그인과 같은 로그인 쿠키를 줘요. 믿을 수 있는 헤더가 있으면 그 사람이 쿠키의 사람보다 먼저예요. 헤더가 없는 요청은 지금처럼 쿠키로 봐서, `headerOnly` 가 아니면 GitHub·QR 로그인과 함께 쓸 수 있어요.
- 로그아웃은 쿠키만 지우고 다음 요청에서 다시 발급돼요. 실제 로그아웃은 SSO 쪽에서 해요.
- 헤더로 들어온 계정은 스킬 저장소를 정할 수 없어요(GitHub 계정이 필요해요).
- 서비스 API(`/api/service/`)와 서버 내부 요청은 헤더를 보지 않아요.
- `origins.extra` 는 trusted-header 가 있어야 쓸 수 있어요. 로그인 쿠키는 주소마다 따로이고 GitHub 로그인은 primary 로만 돌아오기 때문이에요. primary 가 있어야 하고, primary 와 같은 호스트는 안 돼요.
- `origins.extra` 가 있으면 Host 검사는 `/api/health`, 미리보기 출처, 서비스 API 를 빼고 모든 요청에 해요. extra 주소의 `/bridge` 는 연동하지 않는다는 안내와 primary 링크를 보이고, `/api/bridge/*` 는 403 이에요. 설치 스크립트 주소는 늘 primary 예요.
- `auth.headerOnly` 는 trusted-header 가 없으면 시작하지 않아요(아무도 들어올 수 없으니까요). 켜면 로그아웃을 뺀 `/api/auth/*` 가 404, `/api/qr` 가 403, 헤드리스 연동 켜기가 409 예요. 끄기는 돼요. 화면 없는 기기 연결과 폰에서 열기도 숨겨요.
- `headerOnly` 를 켜기 전 검사가 보여 주는 기기는, 마지막으로 헤드리스 연동이 켜져 있다고 알렸거나 상태를 알 수 없는 맥과, 화면 없는 기기예요. 명령줄 `config check` 는 같은 목록을 `headerOnly 전에 끌 기기: …` 줄로 내요.
:::

## 문제가 생기면

- **`모르는 키 …` 로 시작하지 않아요**: 오류 문구 끝에 이 서버가 받는 키 목록이 있어요. 철자를 확인하세요. 새 판에서 생긴 키를 옛 이미지에 넣었을 수도 있어요.
- **`환경변수 X 가 비어 있습니다` 로 시작하지 않아요**: `${X}` 는 비면 시작하지 않아요. 비어도 되면 `${X:-}` 로 쓰세요.
- **`설정 파일 자리가 폴더입니다`**: 없는 파일을 마운트해서 Docker 가 폴더를 만들었어요. 원본 파일을 만든 뒤 다시 띄우세요.
- **`… 서버 사용자(uid 1000)가 읽을 수 없습니다`**: 파일 권한을 `0644` 로 하거나 소유자를 바꾸세요.
- **환경 변수를 고쳤는데 반영되지 않아요**: 파일에 그 키의 값이 직접 적혀 있어요. 운영 탭 맨 위 경고를 보고, 그 키를 `"${환경변수:-}"` 로 바꾸거나 지우세요.
